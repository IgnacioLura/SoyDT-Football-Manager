## Fase 2 — Match replay + process en vivo

**Decisión de arquitectura (replay de partidos)**: a diferencia del original (que genera datos de posición completos para CADA partido simulado y los guarda a disco en `match_results/*.json.gz`), acá el replay se genera **bajo demanda**: `engine_simulate_team_match` (`engine-ffi/src/match_detail.rs`) re-simula el enfrentamiento entre los planteles ACTUALES de ambos equipos (`Team::get_rotation_match_squad_at`, mismo builder real que usa el motor para partidos de liga) cuando el usuario abre la página de un partido — no reproduce el resultado histórico exacto del día simulado. Evita el crecimiento sin límite de RAM del `GameSession` singleton in-memory (sin persistencia a disco). Reutiliza la proyección JSON de `engine-ffi/src/match.rs` (`match_result_json_from_raw`, compartida vía `pub(crate)` con el path JSON-squad existente) para que ambos caminos de simulación serialicen igual.

- [x] SignalR `ProcessHub` — reemplaza el polling de `/api/game/processing` del original (un booleano "¿está procesando?" en loop). `GameController.ProcessLive` (`POST /api/game/process/live?days=N`) corre `GameSession.ProcessDaysWithProgress` en background (loop de a 1 día, reutilizando `engine_process_days` sin cambios en Rust) y empuja un evento `ProgressUpdate` por día vía `IHubContext<ProcessHub>` (hub montado en `/api/hubs/process`, bajo el prefijo `/api` para que el proxy de Vite lo cubra sin config adicional — `vite.config.ts` con `ws: true`). El endpoint síncrono `/api/game/process` original queda intacto (útil para curl/dev-loop). Verificado end-to-end con un cliente SignalR real (Node, `@microsoft/signalr`) contra el contenedor Docker: 2 eventos de progreso recibidos en orden correcto, último con `Done: true`, snapshot confirma el día avanzado. Cableado también en `PipeCheckPage` (sección "Phase 2 — ProcessHub") como demo/verificación manual en browser.
- [x] `AiProgressHub` — implementado como long-poll (`GET /api/ai/progress?jobId=&cursor=`, `AiProgressController` + `AiJobs`), no como hub SignalR: mismo mecanismo que el original (`web/src/ai/jobs.rs::AiJobs::wait`, hasta ~20s de espera revisando cada 500ms), portado 1:1 en vez de forzarlo a SignalR ya que el original tampoco usa push real para esto. Ver detalle completo en Fase 3.
- [x] `GET /api/match/{homeTeamId}/{awayTeamId}` — nuevo `MatchController`, devuelve goles/tarjetas/cambios/posesión + `positionData` downsampleado (~500ms) + `homePlayerIds`/`awayPlayerIds` (para colorear el replay). Sin `match_id` real que buscar (no hay partidos persistidos), así que la ruta usa los dos team ids directo — el frontend los extrae del `matchId` con formato `{date}_{homeId}_{awayId}` que ya usan los links de `TeamSchedulePage`/`LeagueSchedulePage`. Verificado con datos reales end-to-end en Docker (Boca Juniors 1-1 Newell's, goles/tarjetas/cambios reales). Respuesta ~11-12MB sin comprimir por partido (posiciones downsampleadas de ball+22 jugadores) — se agregó `AddResponseCompression`/`UseResponseCompression` (gzip habilitado también para HTTPS, justificado en comentario de `Program.cs`), confirmado ~3.3x de reducción (11.9MB → 3.6MB) con un request real.
- [x] Wrapper PixiJS `MatchReplayCanvas` (`web/src/features/match/MatchReplayCanvas.tsx`) — cancha simplificada (rectángulo + línea media + círculo central, sin césped/gradas), pelota + 22 puntos de jugador coloreados por equipo (azul/rojo), controles play/pause + slider de tiempo, el partido completo (hasta ~95min simulados) se comprime a 60s de reproducción real. `MatchDetailPage.tsx` arma scoreboard + timeline de eventos (goles/tarjetas/cambios) + el canvas. - [ ] Endpoints `/api/match/{id}/metadata` + `/chunk/{n}` — no se implementó chunking: con el enfoque "bajo demanda" ya downsampleado (11-12MB vs ~77MB del original sin comprimir), una sola respuesta HTTP comprimida alcanza; se revisará si hace falta cuando el mundo completo (no solo AR/UY/BR) genere partidos con más jugadores en cancha simultáneamente o si el tamaño se vuelve un problema real de UX.
- [x] **Fix de arquitectura (concurrencia lecturas/escrituras)** — bug real encontrado en verificación manual: `GameSession` usaba UN SOLO lock para todo (lecturas y escrituras), así que un `process` lento (ej. rollover de temporada) colgaba TODA la API, no solo el processing — cualquier `GET` se quedaba esperando ese mismo lock. Arreglado con el patrón real del original (`Arc<RwLock<Option<Arc<SimulatorData>>>>`, clone-then-swap): nuevo export `engine_clone_game` en Rust (`SimulatorData` ya deriva `Clone`), `GameSession.ProcessDays`/`ProcessDaysWithProgress`/`MutateGame` ahora clonan el handle publicado, mutan/avanzan la COPIA, y publican esa copia al final (`Publish`/`CaptureCurrent`, lock solo por el instante de leer/reemplazar la referencia — nunca alrededor de una llamada nativa). Las lecturas (`WithGame`) ya no toman ningún lock compartido con las escrituras; el propio ref-counting de `GameHandleSafeHandle` (`DangerousAddRef`/`Release`) garantiza que una lectura en curso siga usando su handle aunque se publique uno nuevo en paralelo. `WatchlistAdd`/`WatchlistRemove` (las únicas mutaciones directas fuera de `ProcessDays`) migradas al mismo patrón vía `MutateGame` — mutar el handle publicado in-place mientras hay lecturas concurrentes en el mismo puntero sería undefined behavior en Rust (alias `&mut`/`&` entre threads). Verificado con datos reales: 5 GETs concurrentes contra `/api/game/snapshot` mientras corría un `process/live?days=10` en background — todos respondieron en 3-37ms, sin bloqueo.
- [x] Botón "Process" real en el header compartido (`Layout.tsx` vía `ProcessControl.tsx`) — el original tiene este botón en el layout compartido (`#process-btn`, avanza 1 día) más un botón "Go on holiday" (multi-día) en la home; acá se portó solo el primero por ahora. Usa el `ProcessHub` de Fase 2 para progreso en vivo, deshabilita el botón mientras procesa, y hace `window.location.reload()` al terminar (no hay store global que invalidar, cada página fetchea sola). Antes de esto no existía ningún control real para avanzar el día — solo el botón interno de `PipeCheckPage` (debug). El estado de "está procesando" se movió a `ProcessContext.tsx` (montado una vez en `App.tsx`, afuera del router) en vez de vivir en `Layout`, que se remonta en cada página — si no, navegar mientras procesa perdía el estado visual aunque el backend siguiera trabajando. `ProcessBanner.tsx` muestra una franja full-width en el header con "Processing day X of Y… (%)" + barra de progreso mientras hay un proceso en curso.
- [x] **Fix de arquitectura (carrera entre escrituras concurrentes)** — bug real encontrado en verificación manual: el fix de lecturas de arriba (clone-then-swap) resolvió que una escritura lenta bloqueara las lecturas, pero abrió una carrera nueva entre DOS escrituras concurrentes — ej. un `process/live` viejo todavía corriendo sobre el mundo anterior podía terminar y publicar SU resultado encima de un `create` (mundo nuevo) que arrancó mientras tanto, "resucitando" el mundo viejo. Arreglado con un segundo lock (`_writeGate`) que serializa `CreateNewGame`/`ProcessDays`/`ProcessDaysWithProgress`/`MutateGame` entre sí (se toma por toda la duración de la escritura, a diferencia de `_swapLock` que solo se toma un instante) — las lecturas no tocan este lock, así que siguen sin bloquearse. Además `GameSession.TryStartProcessing`/`FinishProcessing` (flag vía `Interlocked.CompareExchange`) hace que `GameController.ProcessLive` rechace un segundo click mientras uno está en curso (mismo comportamiento que el `try_lock_owned` del original) en vez de encolarlo. Verificado con datos reales: `process/live?days=5` en vuelo + `create?countries=UY` disparado a los 300ms → `create` esperó a que el `process` viejo terminara (logs muestran las 5 progress updates completas) y RECIÉN DESPUÉS creó el mundo nuevo (día 1 limpio, sin resurrección del mundo procesado).
